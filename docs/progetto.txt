# Agent Knowledge Base - GoSpin

## Panoramica del Progetto
**GoSpin** è un'applicazione Go per la gestione schedulata dei container Docker. Include un'interfaccia Web SPA (Alpine.js) per la gestione visuale e un'API REST completa per l'accesso programmatico.

### Funzionalità Principali
- **Gestione Container**: Registrazione e controllo di container Docker con nomi friendly e URL
- **Gruppi**: Organizzazione di container in gruppi logici per operazioni batch
- **Scheduling**: Definizione di schedule temporali con timer multipli per target; ogni timer può accendere, spegnere o entrambe le cose
- **Avvio/Stop Automatico**: Container avviati/fermati automaticamente secondo gli schedule
- **Web UI**: Interfaccia SPA moderna costruita con Alpine.js
- **Ghostboard**: Board di testo condiviso per path, sincronizzate in tempo reale via SSE, con persistenza dedicata e API REST
- **API REST**: API JSON completa per accesso programmatico
- **File Watching**: Ricaricamento automatico configurazione quando il file JSON cambia esternamente
- **Graceful Shutdown**: Cleanup appropriato alla terminazione dell'applicazione

## Pattern Architetturali Chiave

### 1. Dirty-Tracking Pattern
- La **cache in-memory** (`internal/cache/store.go`) mantiene una copia dei dati con flag `dirty`
- **I controller HTTP NON persistono direttamente** - marcano solo la cache come dirty
- Una goroutine schedulata (`cache.StartPersistenceScheduler`) salva periodicamente il JSON se dirty
- **Vantaggi**: evita I/O bloccante sulle API, omogeneizza persistenza asincrona

### 2. Interface-Driven Design
Ogni modulo espone interfacce minimali:
- `ContainerRuntime` - astrae Docker/Memory runtime
- `Repository` - astrae persistenza
- `AppStore` - interfaccia cache
- Questo facilita **testing senza Docker** e **mocking**

### 3. Hexagonal Architecture (Ports & Adapters)
- Logica business isolata in `controller/` e `cache/`
- Dipendenze esterne astratte tramite interfacce
- Implementazioni runtime (Docker/Memory) sono intercambiabili
- Pattern Repository astrae la persistenza dati

### 4. Optimistic Locking
- `metadata.lastUpdate` (Unix ms in config.json) previene race condition su modifiche esterne
- File-watching con `fsnotify` rileva modifiche esterne e ricarica automaticamente

### 5. Factory Pattern
- `runtime.NewRuntimeFromConfig(runtimeType, doc, registry)` crea implementazioni runtime appropriate
- Permette switching configurabile tra Docker e Memory runtime
- Facilita testing e deployment flessibile

## Workflow di Caricamento Dati
1. `JSONRepository.Load()` legge `config/data/config.json`
2. Validazione della struttura (tags `validate:"required,url"`)
3. Creazione `DataDocument` in cache
4. Goroutine file-watching per aggiornamenti esterni
5. Goroutine persistence scheduler per salvataggi periodici

## Flusso di Elaborazione Richieste
```
HTTP Request → Gin Router → Controller → Cache Store → Mark Dirty → Response
                                     ↓
                           Background Persister → JSON Repository → File System
```

## Configuration
- **File**: `config/config.yaml` (Viper + dotenv)
- **Env prefix**: `GO_SPIN_`
- **Config path**: via `GO_SPIN_CONFIG_PATH` (default: `./config`)
- **Directory auto-create**: if `data.file_path` does not exist, it is created at startup

### Important variables
- `server.port`, `data.file_path`, `data.persist_interval_secs`
- `misc.scheduling_enabled`, `misc.scheduling_poll_interval_secs`
- `misc.runtime_type` ("docker" or "memory")
- `misc.cors_allowed_origins`
- `WAITING_SERVER_PORT`: second server to expose only the route `/runtime/:name/waiting`.
- `data.actions_mode` ("sync"|"async", default "async"): modalità di esecuzione delle azioni HTTP custom
- `data.actions_timeout_seconds` (default 30): timeout globale per le richieste HTTP delle actions
- `ghostboard.file_path` (default `<dir di data.file_path>/ghostboard.json`): file JSON delle board condivise
- `ghostboard.clear_delay_secs` (default 300): secondi di permanenza del testo dopo l'ultimo client disconnesso
- `ghostboard.max_text_bytes` (default 16777216): dimensione massima del testo decodificato accettato
  per board; il limite del body è derivato da questo valore (6× per gli escape JSON `\u00XX`,
  3× per i form percent-encoded) e lo scarto avviene sul testo decodificato, così un payload con
  molti caratteri da escapare non viene rifiutato se il testo rientra nel limite
- `ghostboard.persist_interval_secs` (default 2): intervallo di scrittura delle modifiche pendenti
- `ghostboard.heartbeat_interval_secs` (default 25): intervallo del commento keep-alive sullo stream SSE

## Main Data Structure
```
DataDocument
├── Metadata (lastUpdate: int64 - unix ms)
├── Containers (name, friendly_name, url, running, active, favorite, pinned)
├── Order (container ordering)
├── Groups (grouping)
└── Schedules (start/stop timers)
```


## REST API Endpoints
| Method | Endpoint | Usage |
|--------|----------|-------|
| GET/POST | `/container*` | CRUD containers |
| GET | `/containers/orphans` | Anteprima dei container registrati ma assenti dal runtime |
| POST | `/containers/orphans/remove` | Rimozione confermata dei container inesistenti |
| GET/POST | `/group*` | CRUD groups |
| GET/POST | `/schedule*` | CRUD schedules |
| POST | `/runtime/:name/{start\|stop}` | Runtime commands |
| GET | `/runtime/:name/waiting` | HTML waiting/redirect page for container or group |
| GET | `/ui` | Web UI SPA |
| GET | `/ui/ghostboard[/:board]` | Pagina Ghostboard; ogni path è una board indipendente |
| GET/POST | `/ghostboard/:board` | Lettura/scrittura del testo di una board condivisa |
| GET | `/ghostboard/:board/events` | Stream SSE con snapshot iniziale e modifiche della board |
| GET | `/homepage` | Configurazione homepage (services, bookmarks, actions, settings) |
| POST | `/homepage/action` | Esecuzione azione HTTP via proxy server-side |

### Details for /runtime/:name/waiting endpoint
- Returns an HTML page (spinner + JS redirect)
- Replaces placeholders `{{CONTAINER_NAME}}` and `{{REDIRECT_URL}}` in the template
- If the container/group is not running, it is started in background
- 404 if not found, 403 if not active, 200 if ok

## Runtime Implementations
- **DockerRuntime**: Uses Moby client, communicates with Docker daemon
- **MemoryRuntime**: Mock for testing without Docker. Non ha un daemon da interrogare, quindi
  `ListContainers` rispecchia il registro (`cache.Store` passato come `ContainerRegistry`): ogni
  container registrato esiste nel runtime, anche se aggiunto dopo l'avvio, e la pulizia dei
  container inesistenti non può quindi segnalarlo come orfano
- **Factory**: `runtime.NewRuntimeFromConfig(runtimeType, doc, registry)` (il registro serve solo
  al MemoryRuntime)

## Web UI (Alpine.js SPA)
- Accessibile su `/ui`
- File: `ui/index.html` + `ui/assets/app.js`
- Tabs: Containers, Groups, Schedules
- Stack: Alpine.js (reattività) + TailwindCSS (styling CDN) + fetch API JSON
- Tab Containers: ordinamento per colonna (nome, friendly name, active, running, CPU, memoria) con direzione invertibile tramite click sull'header
  - I container con `pinned=true` sono **sempre in cima** alla lista, in ordine alfabetico per `name`, indipendentemente dalla colonna e dalla direzione scelte; gli altri seguono l'ordinamento selezionato
  - Il pin è un flag persistito nel registro (`pinned` nel payload di `POST /container`), indipendente da `favorite`; il toggle 📌 in riga e la checkbox "Pin to top" del form di modifica aggiornano il container con il payload completo
  - Il filtro 📌 accanto alla ricerca limita la lista ai soli container pinnati (combinabile con il filtro "solo preferiti"), e la modale di dettaglio mostra lo stato del pin
  - Lo stato dei filtri "solo preferiti" e "solo pinnati" è salvato in `localStorage` (chiave `gosspin.containerFilters`) e ripristinato al caricamento della pagina; se lo storage non è disponibile i filtri partono disattivati

### Ghostboard (ui/ghostboard.html + ui/assets/ghostboard.js)
- Pagina servita su `/ui/ghostboard` (board `default`) e su `/ui/ghostboard/<board>`: ogni path è una board indipendente, con nome validato lato server (`[A-Za-z0-9][A-Za-z0-9._-]{0,63}`)
- Stack coerente con il resto della UI (Alpine.js + TailwindCSS CDN); tema chiaro/scuro persistito in `localStorage` (`gosspin.ghostboard.theme`) e download del testo come `<board>.txt`
- Sincronizzazione: `EventSource` su `/ghostboard/:board/events` riceve lo snapshot e ogni modifica; le scritture locali usano `POST /ghostboard/:board` con debounce di 300 ms
- Ogni tab genera un id casuale inviato nell'header `X-Ghostboard-Client`: gli eventi con lo stesso id sono ignorati, così il caret non salta durante la digitazione
- Le modifiche remote che arrivano mentre ci sono modifiche locali non salvate vengono accodate e applicate dopo il salvataggio riuscito, solo se la revisione è più recente di quella appena scritta
- Alla chiusura della tab il testo non salvato viene inviato con `navigator.sendBeacon`
- Server: `internal/ghostboard` mantiene le board in memoria con revisione e timestamp, fan-out verso i sottoscrittori e timer di pulizia quando l'ultimo client si disconnette; `internal/api/controller/ghostboard_controller.go` espone GET/POST/SSE
- Persistenza: file JSON dedicato (default `config/data/ghostboard.json`), separato dal registry dei container, scritto ogni `ghostboard.persist_interval_secs` solo quando ci sono modifiche pendenti, con prune delle board vuote; un riavvio conserva i testi
- Lo stream SSE non passa dal middleware gzip, non usa il `RequestTimeout` per-request e azzera il write deadline della connessione, così resta aperto oltre il timeout globale del server
- Nessuna autenticazione: chi raggiunge il server può leggere e riscrivere qualsiasi board (da usare solo su reti fidate)

### Homepage dashboard (ui/home.html + ui/home.js)
- Pagina dashboard personale servita su `/ui/home` (e come fallback SPA per ogni `/ui/*` non gestito)
- Contenuto e aspetto configurabili via `config/homepage.yaml` con tre sezioni top-level: `services`, `bookmarks`, `settings`
- `LoadHomepageConfig` normalizza sezioni e liste assenti a slice vuote: la risposta `/homepage` non
  contiene mai `null` per `services`/`bookmarks`/`actions` né per gli `items` di un gruppo, così i
  template Alpine possono iterare con `x-for` anche prima che una sezione sia configurata

### Build metadata (internal/version + -ldflags)
- Le quattro variabili `Version`, `BuildTime`, `GitCommit`, `GoVersion` definite in `internal/version/version.go` (tutte mutabili a link-time) vengono popolate al build tramite `-ldflags "-X ..."`:
  - `Version` ← `git describe --tags --always --dirty` (fallback `0.0.12`)
  - `BuildTime` ← `date -u '+%Y-%m-%d_%H:%M:%S'`
  - `GitCommit` ← `git rev-parse --short HEAD` (fallback `unknown`)
  - `GoVersion` ← `go version | awk '{print $3}'`
- Il `Makefile` espone le stesse variabili (`VERSION`, `BUILD_TIME`, `GIT_COMMIT`, `GO_VERSION`) e le inietta automaticamente nel target `make build`; il `Dockerfile` le riceve come `ARG` per le immagini multi-arch
- L'endpoint `/homepage` espone i quattro valori come **campi top-level** (`version`, `buildTime`, `gitCommit`, `goVersion`), mai annidati dentro `settings`, così l'utente non può sovrascriverli via YAML (test pin di difesa: `homepage_controller_test.go` blocca un tentativo di `version: hax0r...")
- La UI renderizza in footer un'etichetta compatta `v<version> · <short-sha>` con tooltip completo (`build time`, `go version`) al hover
- Temi supportati (in `settings.theme` o via selettore in pagina): `auto`, `tokyo-night`, `catppuccin-latte`, `nord`, `dracula`, `gruvbox`, `night-stars`
- Tre dei temi (`catppuccin-latte`, `nord`, `night-stars`) hanno un trattamento visivo "glassmorphism":
  - **Card translucide**: `--card-bg` e `--card-border` sono `rgba(...)` con alpha, così lo sfondo del tema si intravede attraverso le card
  - **Immagine di sfondo**: renderizzata da uno pseudo-elemento fisso `body.<theme>::before` con `filter` e `opacity` per-tema
- Le immagini di sfondo sono ospitate **localmente** in `ui/assets/themes/<theme>-bg.jpg` (servite dal router statico `r.Static("/ui/assets", "./ui/assets")`) — nessuna richiesta esterna a runtime, la dashboard funziona anche offline / in ambienti air-gapped
- Il valore di `settings.theme` da YAML è trattato come **default**: viene applicato solo finché l'utente non fa una scelta esplicita tramite il selettore (la scelta utente è salvata in `localStorage` sotto `homepage-theme`)
- Lo stato dei gruppi accordion è persistito in `localStorage` sotto `homepage-collapsed-groups`

### Asset locali dei temi (ui/assets/themes/)
- I tre temi "glassmorphism" (`nord`, `catppuccin-latte`, `night-stars`) includono ciascuno la propria immagine di sfondo, **impacchettata nel repository** invece di essere recuperata da una CDN esterna
- Directory: `ui/assets/themes/` contiene `nord-bg.jpg` (≈ 723 KB, 2560×1707), `catppuccin-latte-bg.jpg` (≈ 308 KB, 2560×1945), `night-stars-bg.jpg` (≈ 738 KB, 2560×1628) — JPEG progressivi a qualità ~80
- Routing: la rotta statica `r.Static("/ui/assets", "./ui/assets")` definita in `internal/api/route/ui_route.go` espone tutti i file di `ui/assets/` sotto il prefisso `/ui/assets/...`. Il CSS in `ui/home.html` punta quindi a URL assoluti come `url('/ui/assets/themes/nord-bg.jpg')`; Gin serve i byte direttamente dal disco senza middleware aggiuntivo
- **Totale**: ≈ 3.29 MB su 12 file (3 temi × 4 varianti: JPEG 2560px, JPEG 1280px, WebP 2560px, WebP 1280px). Il browser scarica solo la variante necessaria per ogni cambio tema (via `image-set()`); il service worker pre-cacha tutte le varianti per l'uso offline
- **Nessuna richiesta esterna**: durante il rendering della dashboard **non viene effettuato alcun fetch di immagini verso host terzi**, quindi funziona in ambienti offline / air-gapped. Verificabile con `grep -rn unsplash ui/` (deve restituire zero risultati)
- **Sostituire un'immagine**: basta sovrascrivere il file in `ui/assets/themes/` con lo stesso filename e riavviare il server; nessuna modifica al CSS necessaria

### Ricerca globale (modalità prompt)
- La dashboard espone anche una modalità di ricerca in stile Spotlight/VS Code per saltare direttamente a un servizio o bookmark senza scorrere la pagina
- **Apertura della modale** (solo se il focus non è in un `INPUT`/`TEXTAREA`/`SELECT`/`contenteditable` e nessun modificatore `Ctrl`/`Cmd`/`Alt` è premuto):
  - Tasto `Enter` → apre la modale con query vuota; i risultati appaiono man mano che si digita
  - Qualsiasi carattere alfanumerico (`a`-`z`, `A`-`Z`, `0`-`9`) → apre la modale e **pre-popola** la query con quel carattere; i tasti successivi filtrano i risultati in tempo reale
- **Lista dei risultati**: fino a **6 elementi** per trade-off di usabilità, filtrati live su `data.services` + `data.bookmarks` con ranking per rilevanza (nome esatto > prefisso > sottostringa > abbreviazione > descrizione), tie-break alfabetico
- **Ogni riga** mostra l'icona del servizio/bookmark (con fallback monogramma da abbreviazione o primi due caratteri), il nome, la descrizione e l'etichetta del gruppo
- **Scorciatoie da tastiera** (riportate anche nel footer della modale):
  - `↑` / `↓` — sposta la selezione su/giù
  - `↵` (Invio) — apre il risultato evidenziato in una nuova tab e chiude la modale
  - `Esc` — chiude la modale senza navigare, ripristinando il focus sulla pagina
  - `Tab` — segue l'ordine di focus nativo del browser (cicla input → risultati)
- **Mouse** — cliccare su una riga la attiva come `Invio`; l'hover aggiorna la selezione da tastiera così il prossimo `Invio` apre la riga sotto il cursore
- L'indice di ricerca è ricostruito ad ogni `_loadData` (quindi riflette le modifiche di `config/homepage.yaml` via hot-reload senza refresh manuale)
- Accessibilità: `role="dialog"` + `aria-modal="true"` + `aria-label="Search services and bookmarks"` sulla modale; ogni risultato `role="option"` con `aria-selected` che riflette la posizione della tastiera

### Azioni HTTP custom (Actions)
- La dashboard supporta pulsanti di azione che eseguono richieste HTTP **server-side** (proxy)
- La configurazione è separata in due file:
  - `config/homepage.yaml` → sezione `actions:` definisce nome visuale, icona, descrizione, e una **chiave di riferimento**
  - `config/actions.yml` → definisce i dettagli tecnici: HTTP method, URL, headers, body — **mai esposti al browser**
- Il frontend invia solo il nome dell'azione via `POST /homepage/action { "actionName": "..." }`
- L'`ActionController` carica `actions.yml`, costruisce la richiesta HTTP con i parametri configurati e la esegue server-side
- Se non è definita nessuna azione (file assente o senza voci) il controllo dei riferimenti pendenti
  viene saltato: altrimenti ogni voce di `homepage.yaml` produrrebbe un warning all'avvio; le voci
  senza campo `action` sono ignorate
- Caricamento: il file mancante non è un errore (mappa vuota, quindi ogni nome risponde 404); un file
  invalido lascia il controller senza configurazione e viene ritentato alla richiesta successiva sotto
  lock, così una correzione a caldo non richiede un riavvio e due richieste concorrenti non riscrivono
  la cache nello stesso momento; l'errore viene loggato una sola volta
- Due modalità configurabili via `data.actions_mode`; ogni risposta, anche di errore, contiene `mode`:
  - `sync`: il server restituisce `{mode, statusCode, body}` — la modale mostra status code + body
  - `async`: il server restituisce `{mode, statusCode}` — la modale mostra ✅ OK (2xx) o ❌ KO
- Codici di errore: `400` (`actionName` mancante o JSON invalido), `404` (azione non definita),
  `500` (`actions.yml` non utilizzabile), `502` (richiesta uscente fallita o timeout scaduto)
- Il middleware generico di request timeout può aggiungere un `504` senza `mode` se l'handler
  termina dopo la deadline senza aver scritto; il controller scrive normalmente il `502` prima
- Timeout globale configurabile: `data.actions_timeout_seconds` (default 30s)
- Body letto al massimo 1 MB in modalità sync: il resto viene scartato senza flag di troncamento
  (in `async` il body del target non viene mai letto)
- Vantaggi di sicurezza: headers/token restano lato server, nessun problema CORS, il browser non vede mai credenziali

## Pulizia container inesistenti
- `GET /containers/orphans` confronta il registro (`cache.Store.Snapshot`) con
  `ContainerRuntime.ListContainers` (per il runtime Docker: `docker ps -a`, quindi i container
  fermi contano come esistenti) e restituisce le voci orfane senza modificare nulla
- Con `misc.runtime_type: memory` non viene mai segnalato nulla: il MemoryRuntime rispecchia il
  registro, perché non esiste un daemon esterno con cui confrontarlo
- `POST /containers/orphans/remove` riceve `{"names":[...]}`; ogni nome viene ricontrollato
  contro il runtime prima della cancellazione, quindi un container ricomparso viene saltato e
  riportato in `skipped` (risposta `{"removed":[...],"skipped":[...]}`)
- La rimozione usa `Store.RemoveContainer`, che elimina in cascata le schedule che targettano
  il container e i riferimenti nei gruppi
- Un errore del runtime risponde 500 senza toccare il registro
- Nella UI il bottone **Cleanup** (tab Containers) mostra la lista in una modale di conferma:
  Annulla scarta tutto, solo la conferma esegue la chiamata di rimozione

## Scheduling
- `PollingScheduler` in `internal/scheduler/` effettua polling periodico
- Controllo abilitazione via `misc.scheduling_enabled`
- Intervallo configurabile: `misc.scheduling_poll_interval_secs`
- Timezone: `misc.scheduling_timezone` (default: "Local")
- Ogni timer ha `startTime`, `stopTime`, `days`, `active`; `startTime` e `stopTime` sono
  opzionali ma almeno uno dei due deve essere valorizzato (validato in
  `ScheduleCrudValidator`, altrimenti l'API risponde 400); `active` è obbligatorio, così un timer
  salvato non resta mai con lo stato indefinito (assente = attivo per lo scheduler, ma inattivo
  dopo un reload del file dati)
- Timer con entrambi gli orari: finestra start/stop, anche a cavallo della mezzanotte
  (`isTimerActiveNow`)
- Timer di sola accensione (`isStartOnlyActiveNow`): il target viene avviato all'orario
  indicato e lasciato in esecuzione, nessuno stop automatico
- Timer di solo spegnimento (`isStopDueNow`): il target viene fermato all'orario indicato
  anche se non è stato avviato dallo scheduler (es. container avviato a mano); lo stop
  viene richiesto esplicitamente e salta il vincolo "start già valutato oggi"
- Precedenza: una finestra start/stop che contiene l'ora corrente vince sullo stop-only (dichiara
  la propria fine); un timer di sola accensione invece viene annullato da uno stop-only dovuto
  nello stesso giorno, così il target non viene lasciato acceso fino a mezzanotte
- Rimangono validi i limiti: al massimo un tentativo di start e uno di stop per container
  al giorno (`StartedDayKey` / `StoppedDayKey`), giorni selezionati con `0`=domenica
- Integrità referenziale: `ScheduleCrudValidator` rifiuta con 400 una schedule il cui target
  (container o gruppo) non esiste; il loader (`removeSchedulesWithMissingContainers` in
  `internal/repository/json_repository.go`) elimina comunque le schedule orfane quando legge
  il file, quindi accettarle via API significherebbe perderle al reload successivo
- La cancellazione di un container o gruppo (`Store.RemoveContainer` / `RemoveGroup`)
  elimina in cascata anche le schedule che lo targettano
